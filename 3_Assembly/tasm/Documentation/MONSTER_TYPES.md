# Monster type-byte reference (per-cavern)

The `type` byte at offset +0x04 of each 16-byte monster record in the
MDT is a **per-area slot index**, not a global enemy ID.  Each cavern's
`enemy_id_table` (loaded at game_seg:0x8000 from a per-area SAR chunk
via `LOAD_CHUNK_ES enemy_id_table, 02h` at 200FIGHT.asm:4113) translates
the slot index to a sprite_id + AI handler.

## Discovery: EAI1 is the SHARED regular-enemy AI

After inspecting per-area chunks, the architecture is:

- **EAI1** (`301EAI1.asm`, zelres3 chunk 0x02) is the **shared
  regular-enemy AI handler** used by *all* caverns.  It implements a
  generic state machine (4 states: main / attack_a / attack_b / pincer
  per `crab_ai_dispatch_tbl` at offset 0xA266, indexed by
  `[si+4] & 0xF`).  Same state machine handles slug / bat / frog / rat
  variants by swapping the **frame-pointer tables** (slug_walk_right_frames,
  bat_fly_frames, frog_jump_right_frames, rat_run_right_frames) at chunk
  header offsets.

- **EAI2..EAI8** (`302EAI2.asm` etc.) are **per-boss helper AI** paired
  with the corresponding boss chunk:
  - EAI2 → TAKO octopus boss helper
  - EAI3 → TORI bird boss helper
  - EAI4 → ZELA plant boss helper
  - EAI5 → MEDA / battle-ref chunks
  - EAI6 → mid-range patroller AI
  - EAI7 → fire-AI with hide/projectile behavior
  - EAI8 → multi-pass advance / fire-retreat cycle

So the **same 4 enemy slot indices (0x01..0x04) in EVERY cavern share
the same 4 base behaviors** — only the rendered sprite + per-chapter
stats differ.  Per-area enemy "naming" maps to behavior class:

- **Slot 0x01** → "slow ground crawler" base (slug-class)
- **Slot 0x02** → "fast hopping contact" base (frog-class)
- **Slot 0x03** → "aerial swooper" base (bat-class)
- **Slot 0x04** → "fast ground runner" or "special" base (rat-class)

## What we know from static analysis

**Empirical type-byte distribution** across all 31 cavern MDTs
(generated by `python dump_cavern_inventory.py`):

| level | Used type bytes | Total monsters |
|---:|---|---:|
| 0x01 (prologue / Felishika area) | `0x01:15`, `0x02:16`, `0x03:5` | 36 |
| 0x02 (Muralla, chapter 1) | `0x01:3`, `0x02:24`, `0x03:10`, `0x04:15` | 52 |
| 0x03 (Satono, chapter 2) | `0x01:14`, `0x02:29`, `0x03:19`, `0x73:1`, `0x7C:1`, `0xD0:2` | 66 |
| 0x04 (Bosque, chapter 3) | `0x01:16`, `0x02:13`, `0x03:19`, `0x04:4` | 52 |
| 0x05 (Helada, chapter 4) | `0x01:9`, `0x02:29`, `0x03:21`, `0x04:26` | 85 |
| 0x06 (Tumba, chapter 5) | `0x01:11`, `0x02:24`, `0x03:18`, `0x04:32` | 85 |
| 0x07 (Dorado, chapter 6) | `0x01:12`, `0x02:9`, `0x03:9`, `0x04:28` | 58 |
| 0x08 (Llama, chapter 7) | `0x01:10`, `0x02:34`, `0x03:82`, `0x04:14`, `0xD0:3` | 143 |

**Key facts:**
1. **Slot indices 0x01..0x04** are the standard per-cavern monster slots.
   Each cavern reuses these slots for its own enemy roster.
2. **The same type byte represents DIFFERENT enemies in different caverns**
   (e.g., type 0x01 = Frog in Felishika but probably = Tortoise in Helada).
3. **Special type bytes** (0x73, 0x7C, 0xD0) appear sporadically — likely
   scripted/cinematic enemies or one-off encounters (e.g., the named
   characters or post-boss visitations).

## Specific findings

### Magical Bat is a chest-spawn, not a roster enemy

Per the DB: "Magical Bat — Appears when opening certain chests, attacks
once, flies to ceiling".  100 almas / 255 XP (highest regular enemy
XP).  Mechanism is likely a chest-content type code in the MDT items
table, NOT a roster monster slot.

### Red Slime is unkillable

Per the DB: "Red Slime Monster (Undestructible)".  This implies its AI
handler returns early on the sword-strike hit-test (no HP drain), or
its HP byte is initialized to a value the sword can never reduce.
Worth verifying in the EAI5 code for level 0x05.

### Special type bytes 0x73, 0x7C, 0xD0

These appear sporadically and might be:
- **Stationary NPCs** that turn hostile under certain conditions
- **Boss-cinematic spawns** (e.g., the visiting Akma after Llama)
- **Chest-trigger spawns** (Magical Bat-like)

Cross-reference with `entity_fn_e_*` handlers in 200FIGHT (lines 6755+)
which dispatch based on `[si+4]` byte; the same dispatch likely handles
these special type codes.

## How to verify

To turn this from "tentative" to "verified":

1. **Read each `eaiN.bin` source** (chunks 0x02..0x09 of zelres3) —
   each implements the type-byte → AI handler dispatch.  Decompiled
   chunks live in `working/zelres3/code/301EAI1.asm` etc.
2. **Find the dispatch table** in each EAI: probably `entity_fn_tbl_d`
   or `entity_fn_tbl_e` style, indexed by `[si+4]` low nibble.
3. **Match handler signatures to DB enemies** by behavior (hop-toward
   = Frog, stay-stationary = Slime, fly-from-ceiling = Bat).
4. **DOSBox observation per chapter** — load each save, walk into
   monsters, observe their behavior and sprite, cross-reference with
   the type byte at that MDT coordinate.
